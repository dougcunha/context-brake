## Solution summary

`context-brake run` is a deterministic loop in `core` that drives a plan through successive, fresh non-interactive harness sessions. Each session is one harness process launched with a fixed argument vector and the runner prompt on stdin; the boot arrives through the harness's existing PRD-03 session-start hook. The session ends when the process exits, when the agent's final message is the reset signal, or when the runner stops it at the critical ceiling, a time limit, a token limit, or an interrupt. After each session the runner decides by itself: a session that produced neither the reset signal nor a fresh valid checkpoint stops the run untouched (RF9). Otherwise the runner runs the step's approved validation command, corrects any status the agent wrote without a passing validation (RF5), advances only on a pass (RF4), and applies the anti-loop, session, duration, and token stops. Validation commands run only after the user approves their hashes, recorded outside versioned files (RF14). Per-session records and a run summary live under the existing git-ignored `.context-brake/runtime/`.

The harness boundary is a new `SessionLauncher` port with one implementation per harness adapter folder. Version 1 ships launchers for Claude Code and Codex CLI, the two harnesses whose documentation confirms a non-interactive mode, hook execution inside it, and a session identifier in the stream. The other harnesses are reported as unsupported by `run`, with the reason (DEC-02). `context-brake wrap -- <command>` runs a command inside a runner session and appends that session's telemetry block, using the ledger through the same zone computation the brake uses. Out of scope: parallel steps, re-planning, harness or model switching, cloud or CI triggering, and PR creation (PRD "Fora do escopo").

| DEC-03 | RF2 | The boot comes from the harness's PRD-03 `SessionStart` hook (source `startup`), which both supported harnesses run in non-interactive mode. | DEC-04 | RF1, security | The prompt goes to the harness through stdin. Argument vectors contain only constant flags plus the user's explicit `--harness-arg` values. On Windows, when discovery resolves the executable to a `.cmd` or `.bat` shim (npm global installs), the launcher runs it through `cmd.exe /d /s /c` with each argument quoted, and rejects any `--harness-arg` containing `%`, `^`, `&`, `|`, `<`, `>`, `"`, or a line break with `INVALID_ARGUMENTS`. | Node refuses to spawn `.cmd` shims without a shell. | DEC-05 | RF3 | Session end reasons: `reset_signal` (the final assistant text's last non-blank line, after trimming trailing whitespace, ends with `[REQUEST_SESSION_RESET]` through the runner-only `endsWithResetSignal`; DEC-EXC-CR01), `harness_exit` (exit 0 without the signal), `harness_error` (non-zero exit or a `failed` stream event), `critical_ceiling`, `session_timeout`, `run_timeout`, `token_limit`, `interrupted`. The PRD-02 brake keeps exact-match `hasResetSignal`. The runner stops a session by killing the process tree (`killProcessTree`) after a 10 s grace period that follows a polite signal (SIGINT on POSIX; tree kill directly on Windows). When the reset signal arrives and the process is still alive after the grace period, it is killed. | `process-tree.ts` already kills trees on every platform. Claude Code documents SIGTERM and SIGINT behavior. | Waiting indefinitely for a background subagent could exceed the per-session ceiling. |
| DEC-06 | RF3, RF7 | While a session runs, `LedgerWatcher` polls the session ledger every 1 s through `SessionLedger.readLines` and `summarizeLedger`, keyed by `{harness, sessionId from the started event, agentId: null}`. The first reading in `CRITICAL` starts a critical grace period of `runner.criticalGraceSeconds` (default 120 s), during which the brake allowlist lets the agent save state and commit. The session then ends with `critical_ceiling`. Session tokens are the harness-reported usage when the stream carries it (`measured`), otherwise the ledger's last `usedTokens` (`estimated`). | The brake already confines the agent above the ceiling (`brake-engine.ts:47-52`). The hook writes the ledger out of process, so polling is the only documented coupling. | A filesystem watcher has uneven behavior on Windows and network drives. |
| DEC-07 | RF4, RF5, RF9, CA-02, CA-03, CA-06 | Evaluation order after each session: (1) re-read and strictly validate plan and checkpoint. (2) If the end reason is not `reset_signal` and the checkpoint is not both valid and fresh (`timestamp` ≥ session start), stop with `no_checkpoint` and write nothing (CA-06). (3) Run the approved validation command of the step assigned to the session. (4) Pass: set that step `COMPLETED`, set the next non-completed step `IN_PROGRESS` and `currentStepId` to it, and write atomically. Fail: set the step back to `IN_PROGRESS` when the agent marked it `COMPLETED` or `FAILED`, and record `{stepId, from, to}` as a status correction (RF5). Any other step the agent marked `COMPLETED` without a runner-recorded pass is also reverted and recorded. | The runner never trusts agent-written status (US3). `writeFileAtomically` and the strict validators exist. Stopping before writing keeps the state on disk for diagnosis. | Validating before the checkpoint check would execute commands after an abnormal session. |
| DEC-08 | RF7, RF8, RF10, PI-05 | New optional configuration section `runner`, defaulted like `brake`: `maxSessions` 20, `maxTotalMinutes` 240, `maxSessionMinutes` 30, `maxTotalTokens` 5,000,000, `validationTimeoutSeconds` 600, `maxConsecutiveFailures` 2, `criticalGraceSeconds` 120. CLI flags `--max-sessions`, `--max-minutes`, `--max-session-minutes`, `--max-tokens`, `--validation-timeout`, and `--max-failures` override per run. The published schema changes additively, so existing files stay valid and no version bump is needed. Defaults bound harness-session time to four hours; the final validation overrun is stated in DEC-09. | Flags only would lose per-repository calibration (US7). |
| DEC-09 | RF7 | Limits are checked before each session opens (sessions, elapsed time, tokens) and during it: the session deadline is `min(session start + maxSessionMinutes, run start + maxTotalMinutes)`, and the token total is checked on every ledger or usage update. **Flow.** `run` parses its options, loads the configuration, acquires the lock, and resolves the launcher and executable (CMP-19, CMP-14). Preflight (CMP-04) validates the plan and lists the commands. Approval (CMP-21) prompts or stops. The run record is created. For each session, the loop (CMP-08) checks the pre-session limits (CMP-07), snapshots plan and checkpoint (CMP-16), builds the prompt (CMP-05), and starts the harness (CMP-13) with `CONTEXT_BRAKE_RUN_ID`. It records the session key in `run.json` from the `started` event, watches the ledger and deadlines (CMP-18, CMP-07), and stops the process when needed. It then evaluates the session (CMP-06, running CMP-15 for validation), appends the session line, prints the progress line (CMP-24), and applies the anti-loop and step-approval stops (CMP-07, DEC-17). The loop ends when the plan completes or a stop fires. The summary is printed (text or JSON) and the lock is released. `wrap`, running inside the harness's shell, reads `run.json`, runs the command, and appends the block from CMP-09.

## Contracts and data

- **Configuration** (`context-brake.config.json`, schema version unchanged at 1): the new optional `runner` object has integer fields `maxSessions`, `maxTotalMinutes`, `maxSessionMinutes`, `maxTotalTokens`, `validationTimeoutSeconds`, `maxConsecutiveFailures`, `criticalGraceSeconds`, all positive, strict object, defaults in DEC-08. Validation adds `maxSessionMinutes ≤ maxTotalMinutes`. Existing files without `runner` stay valid. The regenerated schema marks `runner` optional.
- **Plan and checkpoint:** unchanged schemas. The runner writes the plan only in DEC-07 step 4, through the atomic writer, preserving unknown-free strict content as validated. It never writes the checkpoint except to restore a snapshot on interrupt (DEC-12).
- **Runner prompt** (agent-facing, versioned `RUNNER_PROMPT_VERSION = 1`, asserted exactly in unit tests):
  `ContextBrake runner session <n> of at most <max>. Work only on step <id>: <title>. <previous-validation clause> Follow the session boot and the protocol in <protocolFile>. Run commands through "context-brake wrap -- <command>" to see context telemetry. Before ending, update <planFile> and <checkpointFile>, then end your final message with [REQUEST_SESSION_RESET].`
  The previous-validation clause (only after a failure of the same step) is `The last validation of this step failed (exit <code>|timed out). Output tail:` followed by at most 2,000 characters of the kept tail. Budget: at most 800 tokens including the tail.
- **Session log line** and **run summary:** DEC-14 and DEC-15. `bootTokens.source` and `sessionTokens.source` use `measured` or `estimated`. `endReason` and `stopReason` are literal unions derived from constants: stop reasons `completed`, `limit_reached`, `repeated_failure`, `no_checkpoint`, `harness_error`, `step_not_approved`, `confirmation_required`, `interrupted`.
- **Approvals file** `approvals.json`: `{ "v": 1, "approved": [{ "hash": "<sha256 hex>", "stepId": "<id>", "approvedAt": "<ISO>" }] }`, Zod-validated. An unreadable file counts as no approvals and is never silently overwritten (it is renamed to `approvals.invalid-<ts>.json`).
- **Exit codes:** DEC-16.
- **Environment:** `CONTEXT_BRAKE_RUN_ID` (ContextBrake-defined) on the harness process only.

## Integrations and interfaces

- **CLI `run`:** `context-brake run --harness <claude-code|codex-cli> [--approve-commands] [--approve-steps] [--max-sessions N] [--max-minutes N] [--max-session-minutes N] [--max-tokens N] [--validation-timeout S] [--max-failures N] [--harness-arg V]... [--json]`. `--harness` is required, even when only one harness is active, so the runner never guesses (PRD flow step 1). Progress goes to stderr, one line per session: `Session 3 | step 2 "Add parser" | end reset_signal | zone YELLOW | validation PASS | 4m12s`. Decision requests (CA-04) print what happened, the step, the validation output tail, and the options (edit the plan, raise `--max-failures`, rerun `run`).
- **CLI `wrap`:** `context-brake wrap -- <command> [args...]`, with no options of its own. It does not change the child's streams, adds the block after the child's stdout ends, and exits with the child's code. When no command follows `--`, it fails with `INVALID_ARGUMENTS`.
- **Harness processes:** stdin receives the prompt and is then closed. Stdout is parsed line by line through the launcher's Zod schemas (non-strict). Unparseable lines are ignored and counted. Stderr is drained and discarded (never logged). Timeouts follow DEC-05, DEC-06, and DEC-09. Failure policy: a spawn error ends the session as `harness_error`. Missing authentication surfaces as a non-zero exit (Claude Code prints it as the result) and becomes `harness_error` with the first 200 characters of the final text shown on the terminal only.
- **Hooks:** unchanged. The runner depends on the PRD-02 ledger and the PRD-03 boot as they ship.

## Errors, security, and recovery

- **Errors and edges:**
  - Expired authentication or network down: `harness_error`, stop with exit 4 and the hint "check <harness> login and connectivity".
  - Harness crash: the same.
  - Agent marks steps complete: DEC-07 corrections.
  - Validation hangs: DEC-11 timeout.
  - The user edits the plan during a run: re-read each session. A changed command needs re-approval (DEC-10), a removed active step ends the session evaluation with a plan re-read, and an invalid plan stops with `no_checkpoint`-style preservation (exit 4, reason `invalid_state`, folded into `no_checkpoint` for the summary).
  - A session ends without signal or checkpoint: DEC-07 step 2.
  - A stream without a `started` event: no ledger watching; the critical stop is unavailable for that session, recorded as `finalZone: null`, and time limits still apply.
- **User files and sensitive data:** the plan write is the only user-file change, atomic, and limited to the fields DEC-07 names. Logs hold metadata only (DEC-14). Validation output stays in memory and on the terminal. No network activity beyond the harness's own.
- **Command execution:** only approved hashes execute (DEC-10). Approvals cannot be granted by a versioned file.
- **Concurrency and idempotency:** a single run per project (DEC-13). Re-running after any stop resumes from the plan (DEC-12). Evaluating a session is idempotent over the same plan state.
- **Rollback:** the run leaves only runtime files under the git-ignored directory. `remove --remove-state` already deletes `.context-brake/runtime/`. Plan changes are step status transitions the user can revert by editing the plan.

## Risks and open items

- **Risk — total duration overrun (DEC-EXC-CR05):**
  - Probability medium, impact low: validation after the last harness session can run after `maxTotalMinutes` is reached.
  - Bound and mitigation: total elapsed time can reach `maxTotalMinutes + validationTimeoutSeconds + 10 s stop grace`. The `run` text summary states the possible overrun on a `maxTotalMinutes` stop; users can lower the validation timeout.
- **Risk — real harness permissions (PI-04):**
  - Probability high, impact medium: under default modes, real sessions cannot write (Claude Code denies prompts in `-p`; Codex CLI runs read-only), so a run makes no progress and stops by anti-loop.
  - Mitigation: the DEC-18 preflight notice and documented `--harness-arg` examples; autonomy is only claimed on the fake harness.
- **Risk — vendor stream drift:**
  - Probability medium, impact medium: a changed event shape loses the session id or final text.
  - Mitigation: non-strict parsing, a `streamParseErrors` count, and the `started` event missing degrades only the critical stop (time limits still apply). Fixtures are tied to the dated research section.
- **Risk — Windows signal delivery:**
  - Probability medium, impact low: Ctrl+C reaches the console group, including the harness.
  - Mitigation: tree kill while the leader remains alive, and a guarded end-to-end test with a unit fallback. Once the leader has already exited, Windows `taskkill /pid /t` cannot identify its former descendants; that platform limit remains open. POSIX always kills the process group after the grace period or an earlier leader exit (CR-02).
- **Risk — Codex CLI stdin prompt:**
  - Probability low, impact medium: the Codex non-interactive page lists `codex exec "<prompt>"`, but reading the prompt from stdin through `-` must be rechecked in T05.
  - Mitigation: T05 rechecks the vendor docs. If stdin is not documented, the Codex launcher passes the prompt as an argument only when the executable is not a shim, and otherwise fails with `RUN_HARNESS_UNSUPPORTED` naming the shim limitation. That fallback would be raised as an exception HIL if it reduces support.
- **Risk — 20×10 autonomy test duration:**
  - Probability medium, impact low: 200+ fake sessions, each spawning the built hooks, may take minutes.
  - Mitigation: the fake harness runs hooks only on `SessionStart` and one `PostToolUse` per session, and the test lives in the serialized process lane.
- **Open item:** GitHub Copilot CLI, Cursor, and OpenCode launchers are deferred until their vendors document hook or plugin execution in non-interactive mode (DEC-02). Owner: the user, at a future PRD revision. No task in this plan.
