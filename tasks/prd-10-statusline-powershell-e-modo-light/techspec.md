## Solution summary

The status line bridge stops depending on shell syntax. `init` writes only `node "<root>/.claude/hooks/context-brake-statusline.mjs"`. The bridge reads the previous command from its state file and runs it itself, with the same stdin, in the shell that launched the bridge: Git Bash when its environment markers are present, otherwise `pwsh`/`powershell` on Windows, and `sh` elsewhere. It prints the previous command's stdout, or a one-line fallback when that command fails. It records the shell in the ledger, so `doctor` can warn when Claude Code fell back to PowerShell. The PRD-09 pipeline keeps working until the next `init` rewrites it.

Debug mode moves from the instruction-file reference block into the telemetry block, so it works in both modes. `init` defaults to light mode unless the configuration records `"fullMode": true`, which `--no-light` writes. Light mode installs the bridge by default. The hook hosts pick the deadline after mapping the event: 5,000 ms for `session_reset`, 1,500 ms otherwise. They track the running phase, and a `DEADLINE_EXCEEDED` record gets `phase` and `elapsedMs`.

**Status line flow.** Claude Code runs `node "<root>/.claude/hooks/context-brake-statusline.mjs"` in its shell. The bridge reads stdin (up to 1 MiB for parsing, as today) and maps the payload. It reads `claude-statusline.json`. With a `previousCommand`, it resolves the shell (CMP-02), starts CMP-03, and appends the `statusline` ledger line with `shell` concurrently. It writes the previous stdout, or the fallback line (CMP-05), and exits 0. Without a `previousCommand`, it records and prints nothing, as today. With `--pipe` (PRD-09 installs), it behaves exactly as today.

**Hook flow.** The host starts the deadline at 1,500 ms and resolves the root (`project_root`), reads stdin (`stdin`), and maps the event (`event`). For `session_reset`, it extends the deadline to 5,000 ms. It then loads the configuration (`config`), maps the input (`input`), and calls the engine (`engine`). The reset handler marks `ledger`, `prune`, `guidance`, and `boot_*`. On expiry, the failure path records `DEADLINE_EXCEEDED` with the last phase and the elapsed milliseconds, then resolves as today (`deadlineBootDecision`).

## Contracts and data

- **`statusLine` command** (`.claude/settings.local.json`): `node "<root>/.claude/hooks/context-brake-statusline.mjs"`, with `<root>` the real path using forward slashes. `padding` and `refreshInterval` are copied from the previous status line as today. The state file schema (`v: 1`) does not change.
- **Ledger `statusline` line**: adds `shell?: 'sh' | 'git-bash' | 'powershell'`, present only when a previous command ran. `v` stays 1.
- **`errors.jsonl` line**: adds `phase?: string` and `elapsedMs?: integer ≥ 0`, present only on `DEADLINE_EXCEEDED`. Example: `{"v":1,"at":"…","harness":"claude-code","event":"SessionStart","code":"DEADLINE_EXCEEDED","detail":"DeadlineExceededError","phase":"boot_git","elapsedMs":5003}`.
- **Configuration** (`schemaVersion: 1`): adds optional `fullMode: true`. `lightMode` together with `fullMode` → `INVALID_CONFIG` with issue path `fullMode`. The published schema is regenerated and `npm run schemas:check` passes.
- **Telemetry block** (`v3`): with debug on, appends ` debug_line="📊 ContextBrake: 42% · 53760/128000 (harness) · measured · GREEN" (end your reply with this line)`. Without debug, the block is byte-identical to today.
- **Reference block**: never contains the debug line. The block without debug is unchanged, so the managed-protocol and reference hashes of non-debug installs do not drift.
- **Findings** (text and `--json`, `doctor-report.schema.json` unchanged because codes are free strings): `STATUSLINE_BRIDGE_OUTDATED` (warning), `STATUSLINE_POWERSHELL_FALLBACK` (warning), `LIGHT_MODE_DEFAULT_APPLIED` (ok, `init` report), `LIGHT_MODE_DEFAULT_PENDING` (ok, `doctor`).
- **CLI**: no new flags. Accepted from now on: `--light --debug`, `--debug` with light configured, and `--light` with debug on. Full-only options without `--no-light` stay rejected in light mode (PRD assumption), with the existing message naming `--no-light`.

## Integrations and interfaces

- **Claude Code status line**: a command run by the harness shell. It must print the line on stdout, exit 0, and finish before the next update, which cancels it. The bridge limit is 5 s for the previous command. When Claude Code kills the bridge, a still-running previous command can outlive it on Windows; it is short-lived and ends by itself (Risks).
- **Hooks of all process-based harnesses**: `session_reset` gets 5 s, every other event 1.5 s. No output format changes.
- **In-process harnesses (Pi, Oh-My-Pi)**: same deadline selection inside `in-process-host.ts`. There are no synchronous APIs (QA-05).

## Errors, security, and recovery

- Errors and edges: missing or invalid state file → behave as "no previous command". Unreadable ledger for the fallback → payload percentage. Shell executable not found → fallback reason `not started`. Stdout over 1 MiB from the previous command → pass-through truncated at 1 MiB (the status line is one or a few lines). Payload unparseable → still run the previous command with the raw stdin, and skip recording.
- User files: only `init` writes `.claude/settings.local.json`, the configuration, and instruction files, through the change plan (`file-changes.md`). The bridge writes only runtime files under `.context-brake/runtime/`.
- Security: the previous command comes from the user's settings, recorded at `init`. The payload never reaches argv (DEC-14).
- Concurrency and idempotency: a repeated `init` is a no-op in every mode. Concurrent bridge runs append independent ledger lines, as today.
- Rollback: `init --no-light` restores full mode (protocol and reference blocks are recreated), and `remove` restores the previous status line. Reinstalling the previous package version still reads `v: 1` files, but its strict schemas would reject the new optional fields: reinstalling the old version requires deleting `.context-brake/runtime/errors.jsonl` and the session ledgers (Risks).

## Observability and rollout

- Signals: `doctor` findings `STATUSLINE_BRIDGE_OUTDATED`, `STATUSLINE_POWERSHELL_FALLBACK`, `LIGHT_MODE_DEFAULT_PENDING`; `init` finding `LIGHT_MODE_DEFAULT_APPLIED`; `errors.jsonl` `phase`/`elapsedMs`; the `shell` field on ledger `statusline` lines.
- Migration: nothing changes at runtime until `init` runs, because hooks read the configuration as written. The next plain `init` switches full installations without `fullMode` to light mode and rewrites the bridge command. This repository runs `init --no-light` after the feature to keep dogfooding full mode (`DEC-PD-05`).
- Rollout and rollback: released as a minor version; the README calls out the light default and the upgrade notes (the repository has no CHANGELOG). Rollback is `init --no-light` or `remove`.

## Risks and open items

- Risk (medium probability, low impact): the status line PowerShell executable is not documented; if Claude Code uses `powershell.exe` while `pwsh` exists, a previous command that differs between versions could behave differently. Mitigation: `doctor` shows the shell used, and the research doc records the gap.
- Risk (low, low): when Claude Code cancels the bridge on Windows, a running previous command is not killed with it. It ends by itself; the 5 s limit bounds it only while the bridge lives.
- Risk (medium, medium): users of full mode lose the brake on their next plain `init` (`DEC-PD-03`, accepted by the user). Mitigation: the plan asks for confirmation, and `LIGHT_MODE_DEFAULT_PENDING`/`APPLIED` name `--no-light`.
- Risk (low, low): downgrading the package after new fields were written makes the older strict schemas reject those lines. Mitigation: documented in the README upgrade notes.
- Open item: Cursor and Oh-My-Pi session-start timeouts must be at least 5 s. T01 re-checks the vendor docs and records the values in `docs/research/harness-integrations.md`; a lower limit becomes an exception HIL.
